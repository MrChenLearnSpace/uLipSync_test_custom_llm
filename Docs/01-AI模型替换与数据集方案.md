# uLipSync 音频到唇形：自研 AI 模型替换方案

## 结论

可以替换，而且不需要推倒现有的模型表情驱动层。建议保留 uLipSync 的**模型适配与播放层**，将“音频分析 + 音素判定”替换为自研 AI 推理模块；新模块每帧仍输出 `LipSyncInfo`（主音素、音量、各音素概率）。这样 `uLipSyncBlendShape`、`uLipSyncAnimator`、VRM 适配、Timeline 和现有模型配置都可以继续使用。

不建议把 AI 推理硬塞进当前 `LipSyncJob`。该 Job 依赖 Unity Burst 与 `NativeArray`，适合纯数值 DSP，不适合 ONNX Runtime、Sentis 或网络服务等模型推理。应新增独立的 `AiLipSync` 组件，和原 `uLipSync` 二选一。

## 当前项目实际链路

```text
AudioSource / 麦克风
  -> Unity 音频线程 OnAudioFilterRead(float[] input, int channels)
  -> uLipSync.OnDataReceived：取单声道样本，写入环形缓冲
  -> 主线程 Update：调度 LipSyncJob（Burst）
  -> 低通、下采样至 16 kHz、预加重、Hamming 窗、FFT、Mel 滤波、DCT
  -> 12 维 MFCC
  -> 与 Profile 中各音素的 MFCC 原型计算 L1/L2/余弦相似度
  -> LipSyncInfo：phoneme、rawVolume、volume、phonemeRatios
  -> UnityEvent onLipSyncUpdate
  -> BlendShape / Animator / VRM Expression / Texture 等表现层
```

默认 Profile 使用 16 kHz、1024 个下采样后样本（约 64 ms）和 12 维 MFCC。它并不识别完整语音或文字，而是将当前短音频片段匹配到人工校准过的元音/嘴型原型。因此它轻量、低延迟，但在多人声、噪声、辅音、跨语言和自然协同发音上有边界。

关键实现位置：

| 作用 | 文件 | 说明 |
| --- | --- | --- |
| 音频采集、调度、事件输出 | `Assets/Runtime/uLipSync.cs` | 最适合参考输入与事件接口 |
| MFCC 与模板比对 | `Assets/Runtime/Core/LipSyncJob.cs` | 当前待替换的核心 |
| DSP 算法 | `Assets/Runtime/Core/Algorithm.cs` | 当前 MFCC 特征流水线 |
| 音素模板资产 | `Assets/Runtime/Core/Profile.cs` | 人工校准数据与参数 |
| BlendShape 消费者 | `Assets/Runtime/uLipSyncBlendShape.cs` | AI 输出可继续复用 |
| Animator 消费者 | `Assets/Runtime/uLipSyncAnimator.cs` | AI 输出可继续复用 |

## 推荐目标：先做“音频 -> viseme 概率”

不要让第一版模型直接预测每个模型的 BlendShape。不同角色的 BlendShape 名称、数量、风格和最大权重都不同，模型会被角色资产绑死。应将 AI 输出定义为统一的视觉发音类别（viseme），再由每个角色配置“viseme -> 表情”的映射。

推荐初始标签集为 8 类：

| 标签 | 含义 | 常见目标 |
| --- | --- | --- |
| `sil` | 静音/闭嘴 | 嘴部归零 |
| `A` | 张口元音 | `A`、`aa`、JawOpen |
| `I` | 横向/扁口元音 | `I`、`ih` |
| `U` | 圆唇高元音 | `U`、`ou` |
| `E` | 半开前元音 | `E`、`ee` |
| `O` | 圆唇后元音 | `O`、`oh` |
| `MBP` | 闭唇音 | `M`、`B`、`P` |
| `FV` | 唇齿音 | `F`、`V` |

若第一阶段只追求与现有 uLipSync 的兼容，可先做 `A/I/U/E/O + sil` 六类。中文普通话、日语和英语都能通过这套嘴型工作；语言差异主要由标签映射和训练语料覆盖处理，而非必须为每种语言建一整套表情骨架。

## 集成架构

### 方案 A：保持输出兼容（推荐）

新增 `AiLipSync` 组件，职责如下：

1. 从 `AudioSource.OnAudioFilterRead` 或 `uLipSyncAudioSource` 收到 PCM；保持线程安全的环形缓冲。
2. 以固定步长切帧，例如 20 ms 一帧、10 ms hop；准备模型所需的波形或 log-Mel 输入。
3. 调用本地推理（Unity Sentis / ONNX Runtime）或远端推理服务。
4. 后处理：softmax、静音门限、时间平滑、延迟补偿、类别映射。
5. 构造并触发 `LipSyncUpdateEvent`：

```csharp
var info = new LipSyncInfo {
    phoneme = "A",             // 概率最高的 viseme；静音时为 sil 或空字符串
    rawVolume = rms,
    volume = normalizedVolume,
    phonemeRatios = probabilities // 每个标签 0~1，和约为 1
};
onLipSyncUpdate.Invoke(info);
```

然后将 `AiLipSync.onLipSyncUpdate` 连接到现有 `uLipSyncBlendShape.OnLipSyncUpdate` 或 `uLipSyncAnimator.OnLipSyncUpdate`。项目原本的 `Profile` 不再承担识别职责，但仍可作为“标签名称约定”或逐步迁移期间的映射来源。

优点：改动小、可以逐个模型迁移、可对同一模型 A/B 对比。缺点：现有 `uLipSyncBlendShape` 的最终权重仍会乘以音量；如果 AI 已直接预测了最终表情强度，需要关闭/改造该乘法，见“输出设计”。

### 方案 B：AI 直接输出表情通道

模型输出 ARKit 52、VRM Expression 或团队自定义的表情通道向量，由新的 `AiBlendShapeDriver` 直接写入 `SkinnedMeshRenderer` / VRM Runtime。适合有统一角色规范、希望包含下巴、嘴角、微笑、唇压和情绪共发音的项目。

优点：表现上限高。缺点：数据标注与角色规范成本明显高，不能直接复用现有 uLipSync 表情配置。建议在方案 A 稳定并积累数据后再做。

### 推理部署选择

| 场景 | 推荐 | 原因 |
| --- | --- | --- |
| PC / 主机离线或实时 | Unity Sentis 运行 ONNX | Unity 内分发简单，避免请求延迟 |
| 移动端实时 | 量化的轻量 ONNX + Sentis，或原生插件 | 重点控制模型大小、CPU/GPU 和耗电 |
| WebGL | 浏览器侧 ONNX/Web Worker，或服务端 | Unity WebGL 不宜依赖音频线程直接推理 |
| 云游戏、直播、统一模型迭代 | WebSocket/gRPC 流式服务 | 便于更新大模型，但必须处理 RTT 与断网降级 |
| 编辑器批量烘焙 | Python/PyTorch/ONNX 离线工具 | 允许较大模型，结果写为现有 `BakedData` 或新资产 |

实时链路建议总端到端延迟不高于 80~120 ms。典型预算：20~40 ms 音频上下文 + 10 ms 帧移 + 5~20 ms 推理 + 20~40 ms 平滑/播放对齐。远端推理若网络往返超过 50 ms，应作为可选模式，不应是互动场景的唯一方案。

## 模型设计

### 第一版可训练模型

输入采用 16 kHz 单声道音频；每次预测使用 0.4~0.8 秒上下文，中心每 20 ms 输出一个 viseme 分布。特征优先用 80 维 log-Mel，也可直接用 waveform + 小型卷积前端。

轻量网络建议：

```text
PCM -> log-Mel (25 ms window, 10 ms hop)
    -> 2~4 层 2D CNN / depthwise CNN
    -> 2 层 BiGRU 或小型 Transformer Encoder
    -> Linear -> 8 个 viseme logits + 1 个语音活动概率
```

训练损失：加权交叉熵（处理 `sil` 类过多）+ focal loss（可选）+ 相邻帧平滑正则。在线推理若不能使用未来上下文，用单向 GRU 或缓存式 Transformer；离线烘焙可使用双向模型，效果通常更好。

### 输出与表现层解耦

模型应输出：`visemeProbabilities`、`speechProbability`、`rms`、`timestamp`。后处理层负责：

- 将 `speechProbability` 与 RMS 联合判定静音，避免环境噪声张嘴；
- 用 EMA、One Euro Filter 或短时滞后平滑概率；
- 以 `viseme -> 角色 BlendShape/VRM Expression` 配置适配角色；
- 决定“开合强度”由音量、AI 专门的 jaw-open 输出，或两者融合产生；
- 保证所有权重在合理范围并与眨眼、表情动画做加法/优先级混合。

对于沿用 `uLipSyncBlendShape` 的第一版，模型的 `phonemeRatios` 只表示类别比例，张嘴幅度保留给 `rawVolume`。若模型已输出每类强度，则新驱动器应去掉现有“归一化后再乘 volume”的固定逻辑。

## 数据集解决方案

### 数据目标与最小规模

训练“音频 -> viseme”不要求视频是唯一来源，但标签必须能反映真实嘴形。建议分阶段建设：

| 阶段 | 可用数据量 | 标签来源 | 目标 |
| --- | ---: | --- | --- |
| POC | 10~30 小时 | 公开语音 + 词典/强制对齐产生弱标签 | 验证实时链路与 6 类标签 |
| MVP | 100~300 小时 | 多语言语音 + 人工抽检/修正 | 达到可交付的通用嘴型 |
| 产品化 | 500 小时以上，含 20+ 小时视频 | 语音强制对齐 + 视频脸部跟踪 + 人工 QA | 提升辅音、协同发音、不同人群鲁棒性 |

小时数必须按“有效、授权清晰、质量通过”的数据计算。低质量、背景音乐重、转写不准的海量数据，对第一版帮助有限。

### 推荐数据来源组合

1. **自采授权数据（最重要）**：与配音演员签署可用于模型训练、衍生模型和产品部署的授权；录制干净的单人近讲语音。至少覆盖普通话、目标方言/英语/日语等产品语言，男女不同音色、年龄段和语速。
2. **自有业务语料**：经用户授权并脱敏的配音、剧情台词、TTS 文本。它最贴近真实业务文本与录音链路。
3. **可商用公开数据**：仅在法务确认每个数据集、语音和文本的许可范围后使用。不要把“可下载”当作“可训练、可商用、可再分发”。数据卡中应保存来源 URL、许可证版本、下载日期、使用限制。
4. **视频驱动高质量集**：录制正脸高清、30/60 FPS、嘴部无遮挡的视频与同轨音频；用人脸关键点/3D 面捕得到嘴部动作，再人工审核。这是训练“直接输出 BlendShape”所需的核心数据。
5. **合成增强数据**：速度扰动、响度变化、房间混响、轻噪声、编解码损失可增加鲁棒性；不得用增强替代真实多人、多设备、多语言采集。

### 标签生产流程

```text
音频 + 已校对文本
  -> 语言识别/文本规范化
  -> G2P（文字转音素，按语种分别处理）
  -> 强制对齐器输出每个音素的起止时间
  -> 音素到 viseme 映射表
  -> 帧级 soft label（考虑前后音的协同发音）
  -> 人工抽检、问题片段返修、版本化入库
```

普通话建议先用声母/韵母转 viseme 的映射：韵母主要决定 `A/I/U/E/O`，`b/p/m` 对应 `MBP`，`f` 对应 `FV`；舌位类辅音通常不需要独立嘴形。英语应由 ARPAbet/IPA 等音素映射到同一标签集。不要直接把汉字映射为嘴形，必须先经过拼音/音素和时间对齐。

帧级标签应允许过渡，而不是只给硬类别。例如 `/m a/` 的边界附近可以标为 `MBP: 0.6, A: 0.4`，这会直接改善自然度。视频数据可将人脸跟踪得到的嘴部开合、唇圆度、唇宽等连续值，与音素弱标签共同监督。

### 数据格式与版本管理

建议目录与元数据如下，音频与标签绝不只靠文件名关联：

```text
dataset/
  manifests/train.jsonl
  manifests/valid.jsonl
  audio/<speaker_id>/<utterance_id>.wav
  labels/<utterance_id>.json
  mappings/viseme_map_v1.json
  docs/data_card_v1.md
```

每条 manifest 至少包含：`utterance_id`、`audio_path`、采样率、语言、说话人匿名 ID、文本、授权/来源 ID、录音设备类别、噪声等级、切分版本、标签版本。训练/验证/测试集必须按**说话人**切分，不能让同一人的语音同时出现在训练集和测试集。

### 标注与质量控制

- 先自动对齐，再抽检 5%~10%；重点检查爆破音、闭唇音、快语速、静音、语句边界。
- 为每个语种保留固定的“金标集”，每轮模型都在同一批音频与视频上比较。
- 对视频标注，记录关键点追踪置信度、遮挡、头部姿态；低置信度帧不要直接当真值。
- 记录数据删除请求与授权撤回机制，确保能从下一版训练集中排除对应样本。

## 评估标准

模型不应只看分类准确率，还应看用户感知与运行指标：

| 维度 | 推荐指标 |
| --- | --- |
| 识别 | 每类 F1、混淆矩阵、静音误触发率 |
| 时间 | viseme 边界 MAE、音频到表情端到端延迟 |
| 表现 | 人工 MOS/偏好测试、闭唇音命中率、口型抖动率 |
| 性能 | 每帧推理耗时、峰值内存、移动端功耗、模型大小 |
| 鲁棒性 | 跨说话人、跨设备、噪声、音乐、语速、跨语言测试 |

验收时至少同时保留：原 uLipSync、AI 原始输出、AI 加平滑输出三种回放结果。这样可区分模型问题、后处理问题和角色映射问题。

## 建议实施顺序

1. 固定 6~8 类 viseme 标签与跨语言映射表；选定目标角色的 BlendShape/VRM 映射规范。
2. 新建 `AiLipSync`，先使用“假概率/回放 JSON”打通 `LipSyncInfo -> 现有表现层`，无需等待模型。
3. 用 10~30 小时授权音频、自动对齐标签训练离线基线；优先验证标签、延迟和自然度。
4. 导出 ONNX，在 Unity 目标平台完成本地实时推理与性能压测；原 uLipSync 作为回退方案。
5. 扩充真实业务语言、视频和困难样本；再评估直出 ARKit/VRM 表情通道的第二代模型。

## 风险与边界

- 音频不能可靠恢复不可见的舌部动作；viseme 是视觉近似，目标应是“看起来对”，而非逐音素严格一致。
- 唇形与角色表情是两个问题：模型即使准确，错误的 BlendShape 名称、权重或动画覆盖也会造成效果差。
- 远端推理受网络抖动影响，必须有缓冲、超时、静音或本地传统算法回退。
- 训练语音、肖像/视频、转写文本的授权范围不同；收集前应由法务确认训练、商用、模型发布和删除请求处理条款。
- 不要混用未核验授权的网络视频/配音数据；这既是合规风险，也会引入压缩、配乐和角色音效等噪声标签。

## 可直接复用的项目接口

第一版无需改动以下消费组件：

- `uLipSyncBlendShape.OnLipSyncUpdate(LipSyncInfo)`：普通 `SkinnedMeshRenderer` BlendShape。
- `uLipSyncAnimator.OnLipSyncUpdate(LipSyncInfo)`：Animator float 参数。
- `uLipSyncExpressionVRM`：VRM 1.0 Expression。
- `uLipSyncBakedDataPlayer`：离线回放已有烘焙结果；AI 离线烘焙可复用其时间同步思路。

唯一必须保持的是音素标签字符串一致。例如 AI 输出 `A/I/U/E/O`，每个模型的 `BlendShapeInfo.phoneme` 也填相同标签；如采用 `MBP/FV`，需在模型映射中补齐对应项。
