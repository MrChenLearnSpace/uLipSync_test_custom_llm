# uLipSync 接入与自研 AI 升级任务规划

## 目标与范围

本计划分为两个目标：

1. 让团队能把现有 uLipSync 快速接到任意 Unity 角色模型（普通 BlendShape、Animator、VRM、运行时加载模型）。
2. 用自研 AI 替换当前的 MFCC 模板匹配识别层，同时继续复用项目成熟的表情驱动和播放能力。

当前仓库基于 Unity `2021.3.45f2`，uLipSync 包版本 `3.1.1`。现有运行时核心为“音频采样 -> MFCC -> Profile 原型比对 -> `LipSyncInfo` -> 表情驱动”。因此升级范围首先限定在前半段，避免同时重做模型资产、动画系统、VRM 与 Timeline。

## 总体里程碑

| 里程碑 | 目标 | 主要产物 | 完成标准 |
| --- | --- | --- | --- |
| M0 基线跑通 | 可复现原插件能力 | 样例记录、角色映射表 | 指定角色能随 AudioClip 和麦克风稳定口型 |
| M1 模型接入规范 | 任意新角色可配置接入 | 角色口型配置、接入 Prefab/工具 | 新角色不改源码即可接入 |
| M2 AI 接口打通 | 不等训练完成先替换管线 | `AiLipSync`、回放/Mock 数据 | AI 输出能驱动现有三类表现层 |
| M3 数据与离线基线 | 获得可验证的 AI 模型 | 数据卡、标签管线、ONNX 基线 | 离线评测优于或等于基线体验 |
| M4 端侧实时化 | 在目标设备稳定运行 | Unity 推理集成、性能报告 | 达到延迟、帧率、内存目标 |
| M5 产品化 | 可维护、可监控、可扩展 | 回退机制、测试集、发布文档 | 通过验收与灰度测试 |

## Phase 0：建立原项目基线

**建议负责人**：Unity 工程师 + 技术美术；**预计**：2~4 个工作日。

### 工作项

- 在目标 Unity 环境打开 `Assets/Scenes/SampleScene.unity` 与 `Assets/Samples/01. Play AudioClip`，记录可运行状态。
- 选择 2~3 个代表性角色：普通 FBX/GLB、VRM、运行时加载角色。
- 为每个角色整理口型通道：面部节点、`SkinnedMeshRenderer`、BlendShape/Expression 名称、建议最大权重。
- 确定音频场景：预录台词、玩家麦克风、TTS、网络语音、WebGL；每一种都记录目标平台。
- 录制当前 uLipSync 的屏幕回放与性能数据，作为 AI 版本的对比基线。

### 验收

- AudioClip、麦克风（若目标需要）都能产生口型。
- 已知问题被分类为“音频输入、Profile、角色映射、动画覆盖、平台限制”之一。
- 每个试点角色都有一份可复用映射表。

## Phase 1：模型接入标准化

**建议负责人**：技术美术主导，Unity 工程师支持；**预计**：3~6 个工作日。

### 工作项

- 定义统一 viseme 名称：第一版使用 `sil/A/I/U/E/O/MBP/FV`，并明确各语言音素到该集合的映射。
- 定义角色元数据格式（ScriptableObject 或 JSON）：角色 ID、面部渲染器路径、viseme 到 BlendShape/VRM Expression 的映射、最大权重、平滑参数。
- 制作一个接入 Prefab 或运行时装配器；参考 `Samples/10. Runtime Setup` 的动态添加方式。
- 规定动画混合策略：口型在哪个 Update 阶段写入、是否与表情/眨眼叠加、谁拥有最终 BlendShape 权重。
- 用接入清单验证至少三种角色类型。

### 验收

- 新模型接入只需填写配置，不需要改 uLipSync 源码。
- 缺少某个 viseme 时，系统有明确降级映射而不是报错或写错表情。
- 表情动画、眨眼、口型同时播放时没有明显互相覆盖。

## Phase 2：AI 适配层（先于模型训练）

**建议负责人**：Unity 工程师；**预计**：4~7 个工作日。

### 工作项

- 新建独立的 `AiLipSync` 组件；不得修改现有 `uLipSync` 的公开行为，以便可随时切回原算法。
- 复用相同的 PCM 接入模式：同对象 `AudioSource` 或 `uLipSyncAudioSource` 代理，并实现线程安全环形缓冲。
- 定义 AI 输出 DTO：时间戳、`rawVolume`、语音概率、各 viseme 概率、最高类别和推理耗时。
- 将 DTO 转换为项目已有 `LipSyncInfo`，触发 `LipSyncUpdateEvent`；验证能直接连接 BlendShape、Animator、VRM 三类消费者。
- 实现 JSON/CSV 回放模式和随机 Mock 模式，让表现层开发不阻塞于模型训练。
- 增加运行模式开关：`LegacyMfcc`、`AiLocal`、`AiRemote`、`Replay`；至少实现前两种的接口占位。

### 验收

- 同一角色可在 Inspector 或配置中切换原 uLipSync 和 `AiLipSync`。
- Mock/回放概率可以驱动现有角色，音量、静音和概率混合符合预期。
- 音频线程不调用不可线程安全的 Unity API，也不在该线程运行 ONNX/Sentis 推理。

## Phase 3：数据与离线模型基线

**建议负责人**：ML 工程师；**协作**：语音数据、法务、标注人员；**预计**：2~5 周（取决于数据授权）。

### 工作项

- 定义数据卡：数据来源、授权范围、语言、说话人匿名 ID、录制条件、保留/删除规则、已知偏差。
- 建立 `audio + 校对文本 -> G2P -> 强制对齐 -> 音素到 viseme 映射 -> 帧级标签` 的可重复流水线。
- 先收集并审核 10~30 小时授权清晰语音，按说话人划分训练、验证、测试集。
- 定义困难集：闭唇音、唇齿音、快语速、停顿、噪声、混响、背景音乐、各目标语言。
- 训练轻量 log-Mel + CNN/GRU/Transformer 基线，输出 6~8 类 viseme 与语音活动概率。
- 导出 ONNX，并提供独立离线推理脚本，固定输入输出张量名称与形状。

### 验收

- 训练、验证、推理可由清单版本完全复现。
- 测试集严格按说话人隔离，报告每类 F1、混淆矩阵和静音误触发率。
- 与原 MFCC 方案在同一段音频、同一角色上对比，有人工回放结论而不只看分类分数。
- 模型许可证、训练数据授权和分发边界已记录并被确认。

## Phase 4：Unity 本地实时推理

**建议负责人**：Unity + ML 工程师；**预计**：1~3 周。

### 工作项

- 选择目标推理后端：优先评估 Unity Sentis + ONNX；若平台不支持，再评估原生插件或服务端。
- 在 Unity 端实现与训练完全一致的预处理（采样率、单声道、窗长、hop、log-Mel 规范化）。
- 使用滑动窗口/状态缓存进行流式推理，避免每帧重复处理完整上下文。
- 实现 softmax、静音门控、概率平滑、异常 NaN/空输出处理、音频-画面对齐。
- 分 PC、Android/iOS（如适用）、WebGL（如适用）测量每帧耗时、P95 延迟、内存、模型大小和发热/功耗。
- 保留 `LegacyMfcc` 回退：模型加载失败、推理超时、设备不支持或服务断开时自动降级。

### 验收

- 端到端实时延迟达到产品目标（建议互动场景 P95 不高于 120 ms）。
- 不因模型推理造成明显掉帧、持续 GC 分配或音频断裂。
- 同一 ONNX 在离线基准与 Unity 端的输出误差在预设阈值内。
- 断网/模型失败时角色保持自然闭嘴或回退原算法，不发生表情冻结。

## Phase 5：离线烘焙与生产化

**建议负责人**：Unity 工程师；**协作**：内容管线、QA；**预计**：1~2 周。

### 工作项

- 为固定台词实现 AI 离线烘焙工具：音频输入、模型推理、帧级 viseme 概率、资产导出。
- 评估是否复用 `BakedData`：它当前存储每帧音量与音素比率，60 FPS 插值回放；若 AI 输出字段超出其能力，新增版本化资产而不是破坏旧资产。
- 将烘焙接入剧情、过场、TTS 或配音导入流程。
- 制作回归测试资产：固定音频、固定角色、期望概率/口型截图或视频。
- 建立运行日志与指标：模型版本、推理耗时、回退次数、平台、异常原因；避免记录不必要的原始语音或个人信息。

### 验收

- 固定台词无需运行时推理即可稳定播放。
- 内容更新可以批处理烘焙，并能追溯音频、模型、映射和生成资产版本。
- QA 在支持平台完成核心语种、角色、音频输入方式与异常路径测试。

## 角色与责任建议

| 角色 | 主要责任 |
| --- | --- |
| Unity 工程师 | 组件接口、实时音频、推理部署、回退、烘焙与性能优化 |
| ML 工程师 | 标签定义协作、训练、评估、ONNX 导出、模型版本管理 |
| 技术美术 | 角色口型规范、BlendShape/VRM 映射、动画混合、视觉验收 |
| 音频/内容团队 | 语料采集、文本校对、台词资产、困难样本定义 |
| 数据/法务 | 授权核验、数据卡、删除流程、可商用范围确认 |
| QA | 多角色、多语言、多平台、性能与异常路径回归 |

## 关键技术决策（在 M2 前确定）

| 决策 | 推荐默认值 | 原因 |
| --- | --- | --- |
| AI 输出层级 | viseme 概率，不直出角色 BlendShape | 可复用角色表现层，数据成本低 |
| 初始标签 | `sil/A/I/U/E/O/MBP/FV` | 覆盖常见可见口形并可跨语言 |
| 实时输入 | 16 kHz 单声道，20~40 ms 帧 | 性能与视觉稳定性的平衡 |
| 离线输入 | 可用更长上下文/双向网络 | 不受实时延迟限制，质量更高 |
| Unity 推理 | ONNX + Sentis 优先评估 | 易随 Unity 项目分发 |
| 兼容策略 | 新增组件、保持 `LipSyncInfo` | 风险低，可 A/B 和回退 |
| 固定台词 | 优先 AI 烘焙 | 性能稳定、效果可审核 |

## 风险清单与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 数据授权不清 | 无法合法训练或发布 | 数据卡、授权 ID、法务前置审核 |
| 自动对齐错误 | 模型学到错误嘴形边界 | 人工抽检金标集，重点复核辅音/边界 |
| AI 准确但画面差 | 角色映射/动画覆盖造成误判 | 分离评估模型、后处理、角色配置 |
| 移动端性能不足 | 掉帧、发热、延迟 | 量化、小模型、降低推理频率、烘焙与回退 |
| 网络推理抖动 | 互动口型滞后 | 本地模型优先；网络模式做缓冲与降级 |
| 多语言效果不均 | 用户体验不一致 | 按语言/说话人分层评测，逐步扩充语料 |
| API/Unity 版本差异 | VRM 或推理集成无法编译 | 锁定版本矩阵，建立最小编译验证场景 |

## 首个迭代（建议两周）

| 天数 | 可交付内容 |
| --- | --- |
| 第 1~2 天 | 跑通样例、确定试点角色与目标平台、完成角色 BlendShape 清单 |
| 第 3~4 天 | 角色映射配置与动态接入原型，完成普通模型 + VRM 或 Animator 中两类 |
| 第 5~7 天 | `AiLipSync` 接口、Mock/JSON 回放、`LipSyncInfo` 兼容测试 |
| 第 8~10 天 | 10~30 小时 POC 数据方案、标签映射、离线训练/ONNX 可行性验证 |

两周结束时的决策门：若 AI 回放接口、数据授权和小样本离线效果均成立，则进入 M3/M4；若数据尚未就绪，仍可先用原 uLipSync + 标准化角色映射上线，AI 作为独立迭代继续。

## 完成定义（Definition of Done）

项目达到“AI 唇形可交付”需同时满足：

- 目标角色类型均可通过配置接入，且现有 uLipSync 不被破坏。
- 自研模型输出经 `LipSyncInfo` 正确驱动 BlendShape、Animator 和所需 VRM 版本。
- 训练数据来源、授权和标签版本可追溯；测试按说话人隔离。
- 在目标平台达到延迟、帧率、内存和稳定性目标，并有失败回退。
- 固定台词可烘焙，交互语音可实时运行，两个路径都有回归测试。
- 视觉 QA 对目标语言、角色、噪声和异常场景给出通过结论。
